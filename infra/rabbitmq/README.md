# RabbitMQ — PLAT-05

The broker loads the topology generated by
[`scripts/gerar_segredos.py`](../../scripts/gerar_segredos.py) through
[`rabbitmq.conf`](rabbitmq.conf). The generated `secrets/definitions.json`
contains the service account hashes, permissions, exchanges, queues, bindings,
and dead-letter configuration. PLAT-02 owns the generator; its generated
permissions now include the least-privilege Writer retry route used by PLAT-06.

## Status and scope

- The topology and service identities below are the proposed second-bimester
  contracts in `docs/ARQUITETURA.md` §14 and `docs/TAREFAS-2BIM.md` PLAT-05.
- `infra/rabbitmq/plat05/compose.yaml` starts an isolated test broker. It does
  not activate or modify the shared Compose stack.
- The `api` user currently has `read` access to `q.dlq` because the provisional
  `/api/messaging` contract may include a non-destructive DLQ sample. This
  permission depends on BACK, WEB, and PLAT approval. Its `monitoring` tag only
  enables read-only Management API statistics; it does not grant DLQ message
  access.
- Writer retry publication uses a dedicated direct exchange, not the default
  exchange. The writer account is allowed to publish only to that exchange;
  the binding routes the fixed `retry` key back to `q.writer`. The test suite
  also verifies that publishing to `amq.default` remains denied. See the
  [RabbitMQ access-control rules](https://www.rabbitmq.com/docs/access-control).
- This retry exchange is an internal PLAT implementation detail. The shared
  exchange and permission tables in `docs/ARQUITETURA.md` still need the
  responsible fronts' review before this addition is presented as an approved
  cross-front contract.

## Topology

The generated definitions declare seven durable exchanges, including the
Writer-only retry route:

| Exchange | Type | Publishers |
| --- | --- | --- |
| `tv.telemetry` | topic | `gateway` |
| `tv.commands` | topic | `api`, `rules` |
| `tv.insights` | topic | `inference` |
| `tv.events` | topic | `rules`, `inference`, `worker` |
| `tv.jobs` | direct | `api` |
| `tv.writer.retry` | direct | `writer` (routing key `retry`, bound only to `q.writer`) |
| `tv.dlx` | fanout | `gateway` and broker dead-letter routing |

All queues are durable and declared at broker startup, before consumers
connect. `q.writer` binds to `tv.telemetry` with `telemetry.#` and `tv.insights`
with `#`; it receives the JSON envelope for telemetry and insights. Other queue
bindings follow `docs/ARQUITETURA.md` §14.2. Every queue except `q.dlq` has
`x-dead-letter-exchange: tv.dlx`; `q.dlq` binds to that fanout exchange and has
no dead-letter exchange of its own.

The generated permissions follow the least privilege table in §14.3. Service
users cannot configure broker resources. The API can read `q.ws` and, while the
sample contract is pending, `q.dlq`; `gateway`, `writer`, `rules`, `inference`,
and `worker` can read only their assigned queues. Their write permissions are
limited to the exchanges they publish to. Writer can publish only to
`tv.writer.retry`, which routes to `q.writer` with the `retry` key. It cannot
publish to `amq.default` or to the source telemetry, insight, command, or event
exchanges.

## Delivery and failure semantics

Queue durability preserves queue definitions and contents across a broker
restart when its data volume remains in place. Persistent delivery mode marks a
message for disk persistence. The integration test combines durable queues,
persistent test messages, publisher confirms, and a broker restart. These
settings do not provide exactly-once processing, replication, or protection
against every storage or host failure. The test only demonstrates persistence
through the orderly restart it performs.

The Writer uses manual acknowledgements: it acknowledges a batch after the
Influx write returns successfully. On failure it republishes a persistent copy
to the dedicated retry exchange with publisher confirms, waits 1 s before the
first retry and 2 s before the second, increments a bounded retry header, and
preserves the original routing key in a header because the queue delivery uses
the retry binding key. After two retry publications, the next write failure
rejects without requeue, which dead-letters to `q.dlq`.
Invalid messages are also rejected without requeue. If retry publication itself
cannot be confirmed, the original delivery is rejected to the DLQ instead of
being requeued indefinitely. RabbitMQ adds `x-death` metadata
including the source queue, exchange, routing key, and rejection reason. This
does not prevent duplicate Influx writes if a process fails after writing but
before acknowledging; idempotency remains a Writer/data contract concern.

## Automated isolated validation

Run from the repository root in PowerShell:

```powershell
.
scripts\tests\test_rabbitmq_integration.ps1
```

The script creates a uniquely named directory under `$env:TEMP`, asks the
unchanged PLAT-02 generator for local credentials and definitions there, builds
a pinned Python/Pika test client, and starts a broker with the isolated Compose
project name. It copies the generated definitions through `docker cp` into a
uniquely named temporary Docker volume, avoiding a host bind mount of credential
files. The isolated config file is mounted separately so the image's enabled
plugins remain available. It publishes and consumes test messages, checks actual AMQP
permission failures, rejects a message into the DLQ and inspects its `x-death`
headers, verifies requeue after an unacknowledged delivery, restarts RabbitMQ,
and verifies the persistent message and topology again. It then runs
`docker compose down --volumes --remove-orphans` for only its unique project and
removes that exact temporary directory. It does not remove images or resources
belonging to other Compose projects.

## Manual PowerShell validation

These commands start a separate environment that remains available for
inspection. Use the generated credentials locally and do not paste them into
logs or reports.

```powershell
$repo = (Get-Location).Path
$runtime = Join-Path $env:TEMP "tankvitals-plat05-manual"
$env:PLAT05_ENV_FILE = (Join-Path $runtime ".env") -replace "\\", "/"
$env:PLAT05_TEST_MARKER = "plat05-manual-20261102"
$env:COMPOSE_PROJECT_NAME = "tvplat05manual"
$definitionsVolume = "$env:COMPOSE_PROJECT_NAME-rabbitmq-definitions"
$seed = "$env:COMPOSE_PROJECT_NAME-definitions-seed"
$compose = Join-Path $repo "infra/rabbitmq/plat05/compose.yaml"

# Use an empty directory under %TEMP%. Suppress generator output because
# it prints demo-account passwords; service passwords are stored in the files.
if (Test-Path -LiteralPath $runtime) { throw "Refusing to reuse $runtime" }
New-Item -ItemType Directory -Path $runtime | Out-Null
python scripts\gerar_segredos.py --output-dir $runtime | Out-Null
if ($LASTEXITCODE -ne 0) { throw "PLAT-02 secret generation failed" }

docker volume create $definitionsVolume | Out-Null
docker create --name $seed --mount "source=$definitionsVolume,target=/seed" "python:3.12.10-slim-bookworm@sha256:fd95fa221297a88e1cf49c55ec1828edd7c5a428187e67b5d1805692d11588db" sleep 300 | Out-Null
docker cp (Join-Path $runtime "secrets/definitions.json") "${seed}:/seed/definitions.json"
docker rm $seed | Out-Null

docker compose -p $env:COMPOSE_PROJECT_NAME --env-file $env:PLAT05_ENV_FILE -f $compose build test-client
docker compose -p $env:COMPOSE_PROJECT_NAME --env-file $env:PLAT05_ENV_FILE -f $compose up -d --wait rabbitmq
```

Open `http://127.0.0.1:15673` and sign in as `api`, using
`RABBITMQ_API_PASSWORD` from the generated `.env`. Check that the six exchanges
and eight queues appear before any application service connects. The UI and
AMQP listener are bound to loopback only; AMQP uses local port `5673`.

Run these test-client actions one at a time:

```powershell
$composeRunArgs = @("-p", $env:COMPOSE_PROJECT_NAME, "--env-file", $env:PLAT05_ENV_FILE, "-f", $compose, "run", "--rm", "test-client")
docker compose @composeRunArgs publish
docker compose @composeRunArgs consume
docker compose @composeRunArgs reject
docker compose @composeRunArgs permissions
```

`publish` uses the gateway account to send persistent telemetry to `q.writer`;
check the queue's ready count in the Management UI. `consume` uses the Writer
account, prints the test envelope, and acknowledges it. `reject` sends a unique
test body, rejects it without requeue, reads it as `api` from `q.dlq`, and prints
the dead-letter metadata. `permissions` verifies that gateway cannot consume
`q.writer` or publish to `tv.commands`, and that Writer cannot consume `q.dlq`
or publish to `tv.telemetry`.

To check persistence across restart:

```powershell
docker compose @composeRunArgs persist
docker compose -p $env:COMPOSE_PROJECT_NAME --env-file $env:PLAT05_ENV_FILE -f $compose restart rabbitmq
docker compose -p $env:COMPOSE_PROJECT_NAME --env-file $env:PLAT05_ENV_FILE -f $compose up -d --wait rabbitmq
docker compose @composeRunArgs verify-persistent
```

The last command must find the same marker in `q.writer` and then acknowledge
that test message. Stop the isolated broker without deleting its volume:

```powershell
docker compose -p $env:COMPOSE_PROJECT_NAME --env-file $env:PLAT05_ENV_FILE -f $compose down
```

When finished with the manual environment, remove only its RabbitMQ volumes,
seed container (if interrupted before its normal removal), and generated
credentials:

```powershell
docker compose -p $env:COMPOSE_PROJECT_NAME --env-file $env:PLAT05_ENV_FILE -f $compose down --volumes --remove-orphans
$seed = "$env:COMPOSE_PROJECT_NAME-definitions-seed"
if (docker ps -a --filter "name=^/$seed$" --format "{{.Names}}" | Select-String -Quiet "^$seed$") { docker rm -f $seed }
$resolvedTemp = [System.IO.Path]::GetFullPath($env:TEMP).TrimEnd('\') + '\'
$resolvedRuntime = [System.IO.Path]::GetFullPath($runtime)
if ($resolvedRuntime.StartsWith($resolvedTemp, [System.StringComparison]::OrdinalIgnoreCase) -and
    [System.IO.Path]::GetFileName($resolvedRuntime) -eq "tankvitals-plat05-manual") {
    docker volume rm $definitionsVolume
    Remove-Item -LiteralPath $resolvedRuntime -Recurse -Force
}
```

The compose project and volumes have the fixed manual name `tvplat05manual`.
Do not use that name for a different environment. The temporary Python image and
the uniquely tagged integration client image remain in the local Docker image
cache; this workflow does not prune or remove Docker images.
